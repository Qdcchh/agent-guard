# 安全模型与执行状态

状态：GM-MVP-1的规范性安全要求，不是全部要求均已实现或验收的声明。本轮 v1 实施交付时五项修补均标记 FIXED_PENDING_REVIEW，产品自查不是正式接受；具体命令、原失败、JUnit 和67项/60运行义务见 [v1实施报告](../tasks/workflow/runs/local-remediation-20261004/implementation-r1.md)。后续验收与合并结论以 [本轮控制状态](../tasks/workflow/runs/local-remediation-20261004/state.json) 及主控关联的正式报告为准；本文档同步证据见 [文档实施报告](../tasks/workflow/runs/local-remediation-20261004/implementation-docs-r1.md)。整体项目仍 PARTIAL：A2.2公开调用/最终动态查询、A2.3持续签名发布、A3独立锚定/导出/完整采购演示/规模对照实验尚未完成，outbox保持 PENDING。 消息接口以 [实施方案](oauth-oidc-sm2-mvp.md) 为准，测试统一在 [验收矩阵](acceptance.md) 维护。

## 1. 威胁模型

攻击者可控制外部商品描述、报价附件等自然语言和代理输出；可取得普通令牌；可修改、复制、重放、并发发送请求；可掌握一个受限代理的会话私钥。不能因为令牌有签名就假定持有者无恶意。

基础假设：

- AS及其签名密钥、可信企业身份/公钥注册表、网关及其服务密钥、可信状态库未失陷。
- 下游遵守幂等契约，数据库提供事务与持久性，网关和下游相互经过服务认证。
- 独立审计端的密钥与可信检查点未被攻击者共同控制。
- 时钟在声明偏差内，密码库正确实现标准算法，密钥有适当隔离。

安全目标：委托不扩权、令牌与holder绑定、参数不能替换、所有适用祖先额度不超限、同业务键效果不重复、撤销边界明确、执行证据可独立检查。被盗受限代理私钥不能突破自身授权，但不能阻止其恶意消耗已经获准的权限。

非目标与局限：

- 不保证模型不会被提示注入，目标是限制越权业务效果。
- 不抵抗上述可信组件或共同宿主机管理员失陷。
- 不证明采购价格合理、用户授权正确或现实商品已交付。
- 不承诺永久故障下及时恢复或未知状态立即释放预算。
- 不把日志签名有效等同于日志完整；缺少最新可信检查点时不能保证发现回滚。
- 哈希不是加密，低熵数据摘要仍可能泄露信息；敏感载荷须受访问控制，日志最小化。
- 单机容器隔离不等于跨独立组织隔离；同进程代理只展示逻辑身份，不能宣称进程失陷隔离。

## 2. 部署、密钥与信任边界

- 代理分别持有自身客户端凭据和SM2私钥，不持有AS签名私钥、下游管理凭据或账本写权限。
- AS、网关、下游和独立审计端使用不同角色/密钥。单仓库不意味着共享凭据；隐藏端口不能替代服务认证。
- AS授权树与网关账本在同一可信PostgreSQL事务域中协调撤销与接受；下游订单/通知独立事务域，不假定跨库事务。
- DID解析只接受预登记域名/路径，企业注册表确定成员资格和公钥绑定。公钥替换、停用、轮换须管理授权及持有证明，不能自动信任文档中的任意新key。
- 密钥生成、用途、分发、更新、撤销、销毁及泄露处置在实现时补齐运行手册；轮换使用新kid，历史验签保留可信公钥快照，不保留不必要私钥。
- 信任AS、网关和审计公钥应来自独立配置，不得仅信任证据包自己附带的key。SM2/JOSE参数固定，不允许失败时自动降级算法或绕过验权。
- 验权或可信状态库不可用时失败关闭。请求大小、链长和证据大小必须有界；日志不记录明文密钥、客户端secret或可用令牌。

## 3. 根授权与预算不变量

`(tenant_id, task_id)` 永久唯一对应一个根授权。创建时锁任务记录并用数据库唯一约束防止双code并发生成两份根预算。原根过期、撤销、响应丢失或重新同意都不清零重建；新增预算须明确审批新任务。

对根、所有中间祖先及当前节点：

```text
amount_settled + amount_reserved <= amount_limit
calls_settled + calls_reserved <= call_limit
```

计数非负；同一操作最多预留、结算或释放一次。子额度是共享上限，签发时不占用预算。可信报价计算金额；一次新工具操作预留一次调用额度，读取/通知金额成本为0。成功结算为已使用，确定无效果的终局失败释放，未知保持占用。业务次数不替代独立的请求限流及DoS防护。

## 4. 接受事务与线性化

（1）事务前验证令牌SM2签名、JWS类型、固定issuer/audience、AG-Proof、全部业务参数和注册表授权链的静态包含关系。AS统一签各层令牌，不接受旧式父holder直接签发的子凭证。

（2）开始事务，按统一顺序锁定涉及的身份/key状态，再锁根任务及根至叶授权节点。签发、撤销、接受和身份停用遵循同一锁序；仅需部分锁的操作不得反向加锁。

（3）获得必要锁后的接受决定为线性化点。用数据库当前时间（非锁等待前的事务开始时间）重新检查proof、token及全部祖先时效、撤销与密钥状态。原子登记proof jti；多worker必须受同一防重放唯一约束控制。

（4）检查业务幂等键。作用域为租户/任务/tool_id/key；绑定grant_id、holder、tool_version及规范参数。同键同意图返回原操作，不重新预留；同键不同意图或授权节点拒绝。已结算重试不重新要求新操作的余额，但当前验权不得省略。

（5）首次接受：固定可信报价快照，计算成本，校验所有适用节点额度；在同一事务增加全部预留、写入不可变意图、下游稳定操作ID、首次证据关联和RESERVED记录。

（6）提交后才调用下游；提交前崩溃不得产生业务效果。回滚不得保留半份账本变动。

同根串行化优先保证正确性，性能报告应计入其成本，不提前引入分布式锁。换码、委托交换和结果读取也须在各自决定事务内复核新鲜性并登记proof，结果读取不扣业务额度。重放状态仅在覆盖证明有效窗口和时钟偏差后清理。

## 5. 状态迁移与恢复

| 当前状态 | 条件 | 下一状态 | 账本变化 |
| --- | --- | --- | --- |
| RESERVED | worker获得执行权 | EXECUTING | 无 |
| EXECUTING | 下游确认成功 | SUCCEEDED | 预留转已结算 |
| EXECUTING | 终局失败且不可能迟到成功 | FAILED | 释放预留 |
| EXECUTING | 超时、连接中断、结果不确定 | UNKNOWN | 保留预留 |
| UNKNOWN | 查询/同键恢复确认成功 | SUCCEEDED | 预留转已结算 |
| UNKNOWN | 确认终局失败 | FAILED | 释放预留 |
| UNKNOWN | 仍不确定 | UNKNOWN | 保留预留 |

RESERVED中断可恢复原意图；EXECUTING租约失效后查询下游，不直接视为失败。SUCCEEDED/FAILED为终态，不能互换。最终状态、全部祖先账本变动与回执outbox同一个本地事务提交。

签名/审计投递通过持久化outbox重试，receipt_id稳定；回执生成失败不能再下单。业务状态与receipt_status分别表示，回执未生成不等于业务失败。

## 6. 下游幂等契约

- 下游对幂等键、意图摘要、订单/通知及结果使用唯一约束和本地原子事务。
- 接受时固定的可信报价快照（quote_id、版本、SKU、数量、单价、总额及摘要）须与操作意图持久化，贯穿下游执行和所有恢复请求。下游依据相同快照校验，不重新取当前价格替换；快照不可用、版本或金额不匹配不得创建订单。若返回值不一致且可能已有效果，按UNKNOWN对账，不能直接释放预算。下游确认的金额必须等于预留成本，才可按成功结算。成功结果变体还必须匹配工具：ReadResult仅用于两种read工具，OrderResult仅用于order.create，NotificationResult仅用于template.send；共享bind_result与终局执行器均检查该绑定。成功标志不能使变体错配的结果结算：异常保持UNKNOWN与原全部祖先预留，恢复继续原不可变意图，合法结果确认后才结算。
- 同键同意图返回同一效果，同键不同意图拒绝；下游操作ID由网关稳定生成，不由代理任意指定。
- 下游执行和结果查询都只接受网关服务身份。固定模板通知同样必须幂等，不能只给订单加保护。
- “查不到”可能是旧请求仍在飞行，不表示终局失败；应同键恢复/继续查询并保留预算。
- 终局失败要有阻止该键以后成功的持久化终态，不能用连接错误或单次404判定。
- 多恢复者采用租约或版本条件更新。即使重复到达下游，其唯一约束仍防重复效果，网关条件迁移防重复结算。
- 不宣称通用端到端exactly-once；安全结论限于所声明的信任、故障和持久性假设。

## 7. 撤销与外部重试

撤销和接受使用同根锁串行化。撤销提交先于接受决定时拒绝；已接受操作不被撤销回滚，可由内部恢复完成原意图。任一祖先撤销影响后代，不使用放宽生效边界的缓存。

外部调用、交换重试与结果读取仍须当前权限、新proof及有效key。委托幂等命中时也检查已有子节点和接收者，不能重新签发来复活撤销/过期节点。内部恢复与外部重试是不同通道，不使用旧用户签名创建新意图，不增加工具、参数或金额。

## 8. 审计与独立验证

首次接受的token/proof/意图摘要与操作原子关联，重试另记事件不覆盖原证据。最终回执绑定授权、请求、效果和账本变动；规范化ledger_changes及其ledger_sm3、字段、导出与签名格式以实施方案第9.5节为准。证据包含必要的合成参数、结果和每节点金额/次数变动以重算摘要，不在应用日志明文输出原始token或敏感载荷。

成熟版证据记录具有连续序号和前记录摘要。独立审计端保存并签署检查点，至少绑定：profile、checkpoint_id、sequence、head_digest、previous_checkpoint_digest、issued_at及kid。签名采用与其他类型分离的 `ag-checkpoint+jwt`（算法与JWS编码沿用GM-MVP-1），不能接受回执冒充检查点。独立端拒绝序号回退和历史覆盖。

验证方必须独立获得可信最新检查点或最低序号及其签名key，不能只信证据包自带的旧快照。检查关联错配、已锚定记录篡改/重排/删除及相对锚点的回滚；说明未锚定尾部、缺少最新锚点和共同可信组件失陷的局限。

初版若仅完成回执签名而无独立检查点，导出标注UNANCHORED，不声称能检测完整日志回滚。不得把网关自己保存的哈希链当作独立信任域。

## 9. 故障验证边界

至少覆盖：预留提交后中断、下游成功但响应丢失、结算前中断、结算后回执生成失败、回执返回丢失、查无结果后的迟到成功、多恢复者竞争、恢复期间撤销及锁等待超过proof TTL。检查订单/通知效果、每层金额和次数账本、终态、证据关联及检查点；不只检查HTTP响应。具体用例编号统一在验收矩阵维护。
