# 架构与模块边界

当前为设计，除包骨架外尚未实现。首版采用一个代码仓库，按信任边界分离运行权限，不将每个 Python 模块都拆为微服务。

| 组件 | 职责 | 禁止承担的职责 |
| --- | --- | --- |
| contracts / crypto | 模式、规范编码、密码操作、域分离 | 根据自然语言决定业务权限 |
| authorization | 根签发、委托注册、整链验证、管理撤销 | 仅凭模型输出建立根权限 |
| agents | 拆解任务、读取内容、提出签名工具请求 | 直接写预算库或访问下游管理接口 |
| gateway / ledger | 当前验权、原子接受、额度与幂等、恢复 | 将外部超时当成确定失败 |
| tools | 可信商品/报价、模拟订单与通知、下游幂等 | 信任代理申报金额或任意收货对象 |
| audit | 签名回执、独立锚定、离线验证 | 声称签名证明现实商品已交付 |

## 部署边界

- 授权根私钥不交给普通代理或下游。代理身份分别使用独立密钥。
- 网关拥有必要工具服务身份与账本权限，代理没有这些凭据。
- 下游订单状态与网关账本在不同事务域中，不能靠一个共同数据库事务掩盖故障问题。
- 独立审计端有独立密钥、凭据和持久化状态。比赛单机可使用分离容器/账号展示，须承认无法抵抗共同宿主机管理员失陷。
- 不以“隐藏端口”替代服务认证。Compose 网络和权限设计在引入服务时实现并测试。

## 开发依赖顺序

1. 冻结协议与状态机，验证密码库。
2. B 实现密码授权；A 依据同一契约实现账本与模拟下游。
3. 使用仅限测试的替身并行开发，随后替换为真实模块进行端到端验证。
4. 接入确定性三代理，再接真实模型；安全测试不依赖真实模型。
5. B 实现证据核心，A 集成 outbox 与操作回执；C 后期执行独立复现与材料核对。

## 关键设计决定

- 单币种、静态可判的约束集合，避免通用策略语言。
- 根及所有适用祖先共同计账，子额度不在签发时独占资金。
- 同根事务先串行化保证正确性，再按实测决定是否优化。
- 请求 nonce 防重放，业务键保证重试一致性，两者不混用。
- 模拟通知同样有副作用，应有幂等与次数控制，不只关注订单。
- 审计检查点需由验证方独立掌握可信锚点，防止以旧证据包冒充最新状态。

## 首批实现任务

- B：密码库互操作实验及编码测试向量 → contracts/crypto → 根和两级委托 → holder 绑定。
- A：账本模式与迁移 → 原子预算接受 → 幂等模拟订单 → 恢复及撤销串行化 → 三代理集成。
- B/A：签名回执、持久化待办事件、独立检查点、离线验证和故障测试。
- C：按 README 在干净环境复现，整理实测报告、演示材料及缺陷清单。
