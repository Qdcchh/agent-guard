## 先解释为什么不依赖大模型

模型或确定性代理负责“提出工具请求”；授权服务器、网关和持久账本负责“允许哪些请求执行”。本项目验证后者：即使请求不可信，也必须受到密钥绑定、权限范围、共享预算、撤销和幂等约束。确定性输入让相同攻击可重复比较；这不是用假密码或假数据库代替真实执行。

当前没有真实大模型推理，也没有展示真实模型被提示注入后的行为。不能说“模型不会被攻击”；应说“我们限制越权请求造成的业务效果”。若代理的令牌和对应私钥一起泄露，攻击者仍可能消耗其已有授权，系统不保证阻止授权范围内的恶意行为。

## 安全场景讲解顺序

正常采购后，先选“盗取令牌”：有令牌仍必须证明持有绑定私钥。再选“签名后改参数”：签名绑定实际请求，不能签好之后换收货对象或数量。随后讲“委托扩权”：子代理权限只能收窄。

重点展示共享预算：根额度 1,000 元，两个分支各申请 700 元；不能把子代理额度理解为两笔独立资金。查看接受结果、预算与下游效果的检查范围，不只看拒绝状态码。

接着讲重放与幂等：同一 proof 重放被拒绝；合法新 proof 配合相同业务键可找回原操作，不能重复占用预算。撤销阻止撤销提交后的新接受，但不会回滚已经接受的原操作；恢复仍按原意图完成。

最后讲恢复与证据：下游已经成功但回复丢失时，不应立即释放预算或重新下单；不确定状态保留预留，恢复后仍检查唯一效果和一次结算。回执与外部检查点用于检查证据一致性，其真实性边界要同时展示。

页面中的“历史记录回放”只读取既有验证材料；“现场运行”才重新执行固定测试。场景说明中的预期行为与运行观测分列，缺少某项观测时不能用预期补成结果。历史通过不等于当前修改版本全部通过，局部现场测试也不替代最终联合验收。

浏览器打开 **http://127.0.0.1:8765/**。使用这个准确地址；页面仅允许本机访问，不发布公网。若服务已运行，直接打开页面，不必再次启动。

1. 先展示正常流程的“历史回放”：授权链 1,000→800→700 元、四工具 READY、一个订单和一条通知、各级预算结算。
2. 在“安全场景演示台”选择场景，点“读取已有证据”展示有来源的历史检查。建议依次选盗取令牌、签名参数篡改、并发共享预算、撤销、故障恢复。想复跑某类时点“现场运行此场景”，等待真实用例结束；运行期间可讲解请求与防线。
3. 点击“验证原件与篡改副本”，等待真实结果显示“原件通过 / 篡改已拒绝”。展开详情可解释当前授权未知、历史缺口等边界。
4. 时间充裕时点击“启动一次真实演示”。大约 5–8 分钟后会自动切换到新运行结果。运行期间旧记录仍明确标为历史回放，不是本次成功。
5. 新运行完成后再点验证按钮，会验证刚完成的新运行证据。结果带运行 ID 和验证时间。

刷新页面不会中断后台任务，也不会丢失当前服务会话的状态。**重启服务**会读取保留的最近成功正常流程指针，并标为历史回放；场景可再次读取历史证据。之前的运行原件仍在磁盘。执行期间按钮禁用以防重复启动；后端同样拒绝并行动作。若显示失败，不要把旧回放当本次成功。

关闭网页不会停止已启动的后台演示；终端按 Ctrl+C 会停止接收新请求并等待当前演示完成。保持 Docker 和终端运行到任务结束。所有长演示仍受原有有限运行时间约束。

## 现场流程（约 8–10 分钟）

### 1. 用一分钟说明要解决的问题

“多个智能体接力完成采购时，不能因为某个智能体拿到了工具，就允许它任意下单。我们把用户授权、逐级委托、共享预算和执行证据放到网关与持久化账本中，让约束独立于模型本身生效。”

举例：用户总预算 1,000 元；统筹代理给选品代理最多 800 元；执行代理最多 700 元；本次订单 700 元。权限逐级收窄，三个层级都记录同一笔消耗，不能通过拆分代理绕开根预算。

### 2. 启动一次真实演示，运行期间讲架构

```bash
python3 tools/teacher_demo.py
```

它创建新的独占环境，运行真实三代理、两次 AS 委托交换、四工具调用、回执与独立审计导出，最后清理自己的资源。最长运行时间为 15 分钟；首次构建受网络影响。完成后会打印结果目录和摘要。

最后阶段会等待短期授权过期后才交付公开材料，可能有数分钟没有业务输出，这是设计中的等待。不要中途重复启动。需要取消时按一次 Ctrl+C，等待清理完成。

这条命令不是交互式聊天，也不调用大模型 API。演示重点是可信执行边界；不把确定性脚本称为自主推理能力。

### 3. 展示已完成结果（时间紧可直接从这里开始）

上午演练完成后，以下指针指向保留的真实运行：

说明这是结果回放，不是重新发送请求。展示以下事实：

### 4. 现场做证据篡改对照（约一分钟）

```bash
python3 tools/teacher_demo.py --verify "$DEMO_RUN"
```

两次验证都在禁用网络的容器中执行。第一次用公开证据原件，应验证通过；第二次只修改证据副本中的一个数据字符，应被拒绝。原件、独立信任文件和检查点不改动，每次结果另存新目录。

“这说明证据可以脱离在线服务检查一致性，修改后的证据无法蒙混过关。它不意味着可以仅凭签名证明现实世界已收到货物，也不证明当前授权仍然有效。”

这一步依赖本次演练保留的 wheel 镜像。不要在演示前清理 Docker 镜像。若换电脑，需要先在新电脑完整运行一次，并使用新输出的 run 目录。

## 故障预案

若现场构建或新运行失败，保留输出目录，不连续重试消耗演示时间。改用 `--show` 回放上午实跑结果；Docker 可用时继续做 `--verify` 的现场验证。明确区分保存结果与现场动作。

`--verify` 报找不到镜像时，不代表证据本身被篡改；先确认 Docker 正在运行且原镜像未被删除。任何非预期退出码都不能说成验证成功。
