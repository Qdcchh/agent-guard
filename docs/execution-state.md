# 执行状态与事务边界

状态：实现目标，尚无账本或服务代码。与 protocol-v1.md 联合使用。

## 1. 不变量

对根及调用链上每个适用节点：

```text
amount_settled + amount_reserved <= amount_limit
calls_settled + calls_reserved <= call_limit
```

所有状态非负；同一操作最多预留、结算或释放一次。金额成本由可信报价计算。每次新工具操作预留一次调用额度；成功结算为已使用，确定无效果的失败释放，未知保持占用。代理提交请求次数另受限流控制，不以业务次数替代 DoS 防护。

## 2. 接受事务

1. 验证规范编码、完整签名链、权限包含、请求签名与静态参数约束。
2. 开始 PostgreSQL 事务，锁定根任务状态及链上授权节点，顺序固定为根至叶；同根所有接受与撤销操作遵循相同根锁顺序。
3. 锁内重新检查所有祖先撤销与有效期。登记/检查 nonce；nonce 与操作接受在同一事务提交。
4. 查找业务幂等键：存在且意图一致则返回原操作，不再次预留；不一致拒绝。
5. 校验可信报价快照并计算成本；检查全部适用额度，增加预留，写入不可变意图、下游幂等标识及 RESERVED 操作。
6. 提交事务后才允许调用下游。提交前崩溃不得产生业务效果。

v1 优先采用同根串行化实现清晰的正确性，不为吞吐优化提前引入分布式锁。性能报告须承认该串行化成本。事务失败全部回滚，约束及冲突行为必须有自动测试。

## 3. 状态迁移

| 当前状态 | 条件 | 下一状态 | 账本变化 |
| --- | --- | --- | --- |
| RESERVED | worker 获得执行权 | EXECUTING | 无 |
| EXECUTING | 下游确认成功 | SUCCEEDED | 预留转已结算 |
| EXECUTING | 下游确认终局失败且不可能迟到成功 | FAILED | 释放预留 |
| EXECUTING | 超时、连接中断或结果不确定 | UNKNOWN | 保留预留 |
| UNKNOWN | 查询/以同键重试确认成功 | SUCCEEDED | 预留转已结算 |
| UNKNOWN | 确认终局失败 | FAILED | 释放预留 |
| UNKNOWN | 仍无法确定 | UNKNOWN | 保留预留 |

RESERVED 中断可由恢复者继续原意图；EXECUTING 的失效租约由恢复者接管并查询结果，不将其假定为失败。SUCCEEDED/FAILED 为终态，不接受相互转换。最终状态、全部祖先账本变动和回执待签发事件在同一个本地事务中提交。

签名与审计可通过持久化 outbox 重试；必须使用稳定 receipt_id，不能因签名失败重复执行业务。操作成功与回执待生成分别表示，不将缺少回执误判为业务失败。

## 4. 下游契约

- 下游持久化业务幂等键、意图摘要、订单/通知及结果，使用唯一约束和本地下游事务原子落库。
- 同键同意图返回相同效果，同键不同意图拒绝。网关只使用自己生成且稳定的下游操作 ID，不直接信任代理指定下游键。
- 下游仅接受网关服务身份；查询结果与执行请求同样认证。
- “查询不到”不等于终局失败，旧执行可能仍在飞行。此时以同键恢复或继续查询，不释放预算。
- 终局失败必须有阻止该键未来成功的持久化终态，不能仅根据连接错误或单次 404 判断。
- 多恢复者采用操作租约/版本条件更新；即使租约竞争导致下游重复到达，仍由下游唯一约束防止重复效果，账本条件迁移防止重复结算。
- 没有跨库事务，不宣称通用端到端 exactly-once。目标是在明确假设下效果不重复、预算不超限并可恢复。

## 5. 撤销语义

撤销操作在可信状态库事务内获得同一根任务锁并写入撤销状态。接受事务与撤销事务按该锁串行化。

- 撤销提交先于接受事务获得锁：相关新操作拒绝。
- 操作接受事务已提交：后续撤销不撤回既有接受决定，内部恢复可继续完成该不可变意图。
- 外部重试或结果重取仍检查当前权限，已撤销请求拒绝；这与内部恢复是不同通道。
- 内部恢复不得增加参数、金额、工具或操作，不依赖重新使用已过期的用户请求签名去创建新操作。
- 根或任一祖先撤销影响后代。v1 不使用允许延迟生效的撤销缓存。

## 6. 恢复验收

至少注入：预留提交后中断、下游成功后响应丢失、结算前中断、结算后回执生成失败、回执返回丢失、查无结果后迟到成功、两个恢复者竞争、恢复期间撤销。每项检查订单数、各祖先金额及次数账本、操作终态和回执关联，而非只检查 HTTP 响应。
