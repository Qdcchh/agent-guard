## Minimal implementation route

1. Keep the six-field GM-MVP-1 invocation and existing AGPoP semantics. Introduce a separately versioned, bounded detached approval header and action domain (V2 if extending the current Rust V1 schema). An approval binds the exact normalized request intent/parameters, tenant/task, trusted root-to-leaf authority facts, holder/kid, audience/tool/version, business key, trusted quote/currency/cost, action ID, trusted policy/epoch and expiration. Fresh AGPoP proofs remain required on retries; approval need not bind the replaceable proof nonce. Cross-language tests must construct message bytes independently of the serialized fixture's incidental field order. A compact digest of complete canonical parameters can avoid duplicating the 256-item body in a header; explicitly preserve or document size limits. Reject duplicate approval headers as sensitive headers, duplicate JSON keys, unknown fields, wrong numeric types and alternate invalid encodings.

2. Trusted operator configuration chooses required order approval and the group key/policy/epoch. Existing /v1/invocations must enforce this same policy; do not add a second protected route while leaving it unprotected. Missing configuration preserves explicitly documented old deployments; the new demonstration assembly must require populated valid configuration. Reject malformed/partial configuration at startup. Per-request verification must never choose trust from a request-carried key.

3. Verify the real FROST-compatible Ed25519 group signature with a mature pinned library outside DB locks, then carry immutable verified approval facts into the acceptance transaction. Compose the per-call callback using TrustedAcceptBinding.compose, preserving the original evidence descriptor and validator. Do not replace it with an untyped callback or shared mutable service field. Compare approval against the actual inserted/existing operation and authoritative permission path in that callback. In particular use the existing operation's immutable quote/cost for retries rather than today's catalog.

4. Add a new migration for durable action-ID → operation/message binding, with unique scope/action identity and immutable operation association. Persist exact approval material or its explicitly documented evidentiary representation with the operation/evidence link, in the same transaction as reservations. Same action plus same operation/message may retry with fresh current authorization; changed intent/business key/operation must reject. Never overwrite the original binding with an upsert. A failed transaction must roll back proof registration, approval consumption, budget changes and links together. Include migration in explicit wheel data and bundle/lineage manifests; do not edit earlier SQL.

5. **Final-clock ordering is the main implementation trap.** The present callback runs before journal append, deferred constraints and the ledger's final authorization clock. Checking approval expiry only in that callback is insufficient. Extend the trusted binding/final check minimally so the approval deadline is checked using the final DB time after all potentially blocking dependency work, for CREATED and EXISTING. Preserve the existing final grant/proof checks. Do not mutate VerifiedInvocation proof-expiry fields to smuggle this deadline: evidence context is already fixed. No network signing or other external work under locks. Internal worker recovery remains tied to the accepted immutable operation and does not request fresh approval.
