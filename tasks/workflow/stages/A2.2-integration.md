# A2.2-integration：待单独批准的后续阶段

当前业务实施未授权。A2.1及B补正已验收并合并；可在已有规划授权内建立 DRAFT 包并独立审包，只有用户明确批准本段实施且包审通过，才能按获批版本冻结并派发。主控须先重新核对B实际提交/接口、完整SDK验收、可信权限快照与证据归属、result-read契约；不能因基础JWS代码已推送就当依赖齐全。

范围以原A2任务为准：真实B invoke/result-read验证器、grant/token/祖先绑定与收窄、生产失败关闭装配、固定可信HTTPS端点和严格HTTP/错误契约、授权查询零业务计数及proof新鲜性/重放。完整P15、P16、P17、适用P21及全部已验收核心/A1回归需要独立实测。若P21完整闭环依赖真回执，其完整结论留A2.3，不能部分冒充全通过。

草拟时要把全部必需ID、接口边界、依赖提交和验收方案写入本阶段版本化任务包，并如实标明授权状态，经新reviewer审包，state expected_requirement_ids/contract_files随该批准版本冻结。未齐B保留BLOCKED；不造假VerifiedInvocation、不放宽A1 purpose、不使用请求自报权限或跳过TLS/验权。

本阶段只允许批准范围内的实施、详细独立复核、补正和再复核。通过后A2整体仍按真回执/联合测试缺口PARTIAL，停下来等用户批准A2.3。commit/push/PR/合并仍需单独明确授权。

## 建包时必须具体化的交付

1. 从 main 的 B 补正基线检查现有验证器、权限快照、证据绑定与查询投影；列出可直接复用部分和真正缺失的公开入口，不重复实现密码/授权核心。
2. 冻结 invoke/result-read 的请求、响应、202 与错误语义、固定 HTTPS endpoint、配置校验和启动失败关闭；以原 A2/接口文档为依据，歧义先解决，不能临时发明协议。
3. 请求验签到事务最终接受/查询之间的可信数据传递明确；等待锁后重新检查 proof TTL、撤销、holder/key 状态及全部祖先约束。查询必须零新增业务计数，仍验证当前权限与新 proof。
4. 真 HTTPS 黑盒正负链路覆盖 P15/P16/P17；P21 每个子断言逐项标“本段完整覆盖”或“依赖 A2.3 未完成”，不把整个 P21 标 PASS。参数篡改、重放、跨租户/holder、候选重试、错误配置均观察真实效果/预算/证据变化。
5. 在正式矩阵列出全部前段回归及 B 补正六项问题；保留真实 PG、进程恢复、并发、迁移与 source/wheel 验证。沿用需求与断言，不锁死历史测试总数。
6. 提交可复现启动/调用说明、配置来源、独占测试资源、详细证据和当前文档。下一步交 A2.3 的接口、未闭合断言与故障边界必须明确。

本文件仅为阶段指引，不是正式任务包；获批后按模板冻结精确文件清单、依赖哈希、每项断言及测试位置，并依据 [现行约定](../current-policy.md) 解决下一阶段运行门与适配授权。
