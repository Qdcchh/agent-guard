# 独立阶段验收契约

本契约供 GPT-6.1 Sol xhigh reviewer 与主控直接遵守。它约束审查与证据，不替代原始需求、安全模型、阶段任务或用户授权。主控为 GPT-6.1 Sol high，实施者为 GPT-6.1 Sol medium；当前角色与运行边界见 [现行约定](current-policy.md)；每个大阶段之间必须停下等待用户明确批准。每次调用必须明确 `review_kind`，不能把审任务包和验实施结果混为一轮。

## 0. 两种审查必须分开

| review_kind | 时机与对象 | 必须做什么 | 结论与保存路径 |
| --- | --- | --- | --- |
| `PACKAGE_REVIEW` | 首次实质实施前，对版本化 Markdown 包及原始需求、既有基线作独立审查 | 核对需求ID完整性、原始安全语义、方案/接口/所有权/范围、依赖真实性、验证与隔离设计、授权边界及包/契约指纹；读必要实际基线代码、调用方和既有测试 | `PACKAGE_READY` / `PACKAGE_CHANGES_REQUESTED` / `BLOCKED`，主控保存 `runs/<stage>/package-review-rN.md` |
| `IMPLEMENTATION_ACCEPTANCE` | 实施/补正停写并冻结完整候选版本后 | 本契约的完整需求矩阵、深度代码与调用链检查、独立真实执行、探针、历史缺陷与整体回归、开始/结束指纹与资源核验 | `ACCEPTED` / `NOT_ACCEPTED` / `BLOCKED`，主控保存 `runs/<stage>/review-rN.md` |

- 包审不得要求尚未实施的 A2 行为已经通过，也不创建运行环境、启用业务资源或实施业务代码。包审的运行矩阵是验证计划，不是已经运行的证据；尚未实现的测试记“计划，未执行”，不能因此把包审自动判 BLOCKED，也不能写成行为 PASS。
- 配置授权范围内的包草拟/只读审查可以发生在业务实施授权 `PENDING` 时；必须准确注明 pending，不能为通过包审补造 GRANTED。若已有真人授权，检查包是否与它一致；包审本身不能授予实施或下一阶段权限。
- 首次实施前必须有无阻断的 `PACKAGE_READY` 和独立真人实施授权，二者对应同一阶段、范围、包版本与契约指纹。包审补正改动后新开 reviewer，不能沿用旧包结论。包范围改变且超出现有真人授权时由主控重新交用户批准。
- `PACKAGE_READY` 不能设置阶段 ACCEPTED、关闭实施缺陷、通过 `--require-accepted` 或替代后续完整独立实跑。下文关于实跑、故障/并发/进程验证、阶段PASS/ACCEPTED的硬门槛专用于 `IMPLEMENTATION_ACCEPTANCE`，该模式不得引用包审例外豁免。

## 1. 当前范围与依据

- 当前 B 补正已经独立验收并合并；以 [context](context.md) 和 [现行约定](current-policy.md) 识别当前阶段与授权，不从 A2.1 历史 state 重新开工。
- 必读工作流入口、AGENT.md、HANDOFF、当前正式任务包与独立需求矩阵、原 A2 任务全篇、安全/接口/验收文档、前段正式验收与问题台账、实际代码及测试。下一阶段未获批准时仅可做已授权的文档规划，不实施业务。
- 第6节的31项清单和专项是`A2.1-core`专用。后续阶段必须由真人批准后的正式阶段文档/版本化任务包及`state.expected_requirement_ids`生成完整当段矩阵，保留前段回归并增加本段真实验权、HTTP或签名义务；不能直接沿用或删减这31项冒充后续完整要求。A2.2/A2.3提纲仅为提案，不是已批准开工包；不能仅凭提纲启动实施或准备业务资源。
- 主控核对当前平台真实用户消息后记录 `source_message` 与阶段授权；worker/reviewer 不能自填、补造或用其他代理的要求冒充真人批准。实施验收检查所传阶段与该授权一致，无法确认时报告 BLOCKED；包审允许如实记录尚待批准，不等同放行实施。
- 文件中的旧完成状态、测试数量或实施报告不是当前事实。明确区分最新正式结论、历史失败证据、目标设计与实际实现；要求冲突无法据最新授权消解时报告阻碍，不自行弱化标准。
- 不 commit、push、创建 PR、合并、修改 Git 配置或分支保护。不修改或复制尚未验收的 B 模块，不用替身装配生产 HTTP，不伪造签名、摘要、验权成功或 SDK 完成。

## 2. 独立性、冻结与版本绑定

1. 主控先确认实施者和其他 writer 已完成并停止写入受审文件，再提交包/候选版本。包审期间包及关联契约冻结，实施验收期间全部候选代码与契约冻结；审查期间禁止交叉写入。
2. 每轮使用新的 reviewer Task／子会话，不复用上一轮 `task_id`。新的 reviewer 接收完整原始任务、当前阶段范围、全部需求矩阵、历史问题台账、候选版本清单与证据目录，不只接收实施者的成功总结。
3. 主控准备只读清单：仓库绝对路径、阶段 ID、轮次、分支、HEAD、相对基线的 staged/unstaged diff、`git status --short`、全部有关未跟踪新文件、删除及重命名、逐文件 SHA-256 与清单 SHA-256。HEAD 只是基线，不能独立代表未提交实现。
4. 指纹覆盖本次候选源代码、迁移、测试、fixtures、依赖/配置、阶段需求以及影响判断的既有调用方。未改变但受影响的依赖也要检查；不能只散列 diff 而漏掉未跟踪文件或周边代码。
5. Reviewer 在审查开始与结束独立核对清单、实际文件内容、Git 状态和指纹。不能把主控提供的指纹当作已验证事实。受验收文件缺失、出现新改动、fingerprint 不符或 writer 未停止时，本轮结论无效，返回 BLOCKED，重新冻结并新开审查。
6. Reviewer 不修改受验收源码、正式测试、需求、正式报告或问题台账，不调用其他 agent。允许经 shell 写入本轮自建且可确认归属的 `artifacts/workflow/<run-id>/` 临时探针、缓存、日志/XML与合成数据，也可使用仓库外自有临时目录与隔离资源。证据目录明确列入快照排除白名单；不能用 shell 或白名单绕过只读边界修改受审文件。运行命令前确认写入目标符合边界。
7. Reviewer 返回完整 Markdown 审查，使用 [审查模板](templates/review.md)。主控按review_kind原样保存到 `runs/<stage>/package-review-rN.md` 或 `runs/<stage>/review-rN.md`，stage 使用本轮已批准阶段 ID，然后写摘要与问题台账，不能只保留“无问题”或删去缺口；保存报告不改变已冻结版本。若文件内容被截断或关键矩阵缺失，本轮尚未完成。返回报告的文件链接使用仓库绝对路径或与最终报告位置相符的相对路径，不能照搬模板所在目录的相对链接。

## 3. 必须直接查证的内容

- 从原始需求建立完整矩阵，逐项标记是否属于当前阶段、关联实现/调用方/测试、需要观察的数据库与业务效果、验证方法与证据。不得漏项，或把未验证项悄悄移出本阶段。
- 阅读实际 staged/unstaged diff 和未跟踪文件；阅读周边调用链、输入来源、可信边界、失败路径、状态机、锁序、迁移、资源生命周期及现有测试断言。不能只审查新增行、接口名字或实施报告。
- 按语义核对测试：否定路径确实触发了目标条件；并发使用独立连接与 barrier/event；次数和金额逐祖先检查；真实下游效果、操作、事件和 outbox 一起断言。测试名称或全绿计数不能替代这些证据。
- 对缺失覆盖或可疑语义，可在自有临时目录增加独立探针并在自有隔离资源复现；先确认安全目标，不对共享库或无关容器实施破坏性实验。确需仓库正式回归时返回要求，由实施者补入，然后新轮复验。
- 提供具体缺陷的触发条件、文件/行号、影响、证据/最小复现与修复要求。区分已确认缺陷、待核实疑点和非阻断建议，不为凑数量制造问题，也不因为报告声称完成而降低审查深度。

## 4. 证据等级与实际验证

每条证据必须明确归类，不能混写：

| 等级 | 含义 | 允许的结论 |
| --- | --- | --- |
| 本轮独立实跑 | Reviewer 对冻结版本亲自执行，记录命令、环境、退出码、pass/fail/error/skip、日志/XML与内容指纹 | 能支持其实际断言范围内的通过或失败 |
| 本轮独立静态查证 | Reviewer 直接读实际实现、调用方、测试或数据库结构 | 能支持所查证的代码/设计事实，不替代要求实跑的行为 |
| 既有日志核对 | 查看实施者或历史 reviewer 日志，核对版本、环境、命令及结果 | 只能表述“日志记录／已核对”，不得写成本轮独立重跑 |
| 未执行或无法执行 | NOT_RUN 或 BLOCKED，注明原因、影响与恢复条件 | 当前阶段必需项未闭合，不能通过 |

- 测试计数按本次实际收集与执行报告，区分 unit/integration/独立探针/skip；不把 A1 的旧 68＋78 或其他固定总数作为验收门槛。
- 分层替身、抛异常注入、真实 PostgreSQL 回滚、进程强制终止、真实断网与 TLS 部署分别记录。不得把模拟异常称为真实网络故障，或把普通 JSON 字节称为 RFC8785 编码。
- 最终阶段放行前，本轮 reviewer 必须独立运行该阶段要求的检查与关键行为、回归和独立探针。仅核对实施日志不足以代替必需实跑；无法安全运行则 BLOCKED，不把未运行写成 PASS。
- 修复轮可先针对缺陷及影响范围验证，但最终判断仍须更新完整矩阵并完成本阶段的整体必跑检查；不能只关闭历史问题而不检查新增回归。
- `WF-PY311-ENV` 必须实际验证 Python 3.11 与新依赖安装/锁定。缺少环境或安装不能完成时当前阶段 BLOCKED，不把历史 Python3.11 CI或其他Python版本结果作豁免。尚未授权的远程 CI 仅记录 NOT_RUN，不虚报通过，也不把它另加成本地阶段阻断要求。

## 5. 测试资源与数据安全

- 使用本轮独立真实 PostgreSQL16 实例或经明确确认的独占测试命名空间。记录容器 ID、Compose project/service/配置来源、挂载、随机库/schema、归属标记与资源清单，测试前检查目标和所有权。
- 不沿用默认共享 Compose project；A1 与 A2 project 必须隔离，reviewer 自建实例也要独立命名。不同 container_name 或端口不能代替 project 隔离。
- 清除普通／部署 `AGENT_GUARD_DATABASE_URL` 等可外溢配置，只注入本轮 TEST DSN；不得打印密码、完整 DSN、token、私钥或敏感日志。日志、数据库断言与合成数据均脱敏。
- 网关与模拟下游是独立数据库/连接/事务域，不能靠同一事务冒充跨域恢复。
- 只清理本轮成功创建、身份与归属可核对的资源，不 docker prune、批量 stop、共享 project down、清空既有库或改安全断言去使用共享库。既有容器、测试库和成员资源保持不变；无法确认归属时先报告阻碍。

## 6. 仅 A2.1-core 使用的矩阵与历史回归

仅在`current_stage=A2.1-core`时，矩阵必须与 [阶段计划](stages/A2.1-core.md) 及`state.expected_requirement_ids`完全核对，至少包含 `A2-P01`—`A2-P14`、`A2-P15-CORE`、`A2-P19`、`A2-P20`、`A2-CKPT1-OBL01`—`A2-CKPT1-OBL06`、`WF-A1-REGRESSION`、`WF-INDEPENDENT-PROBES`、`WF-QUALITY-CHECKS`、`WF-PY311-ENV`、`WF-RESOURCE-ISOLATION`、`WF-IMMUTABLE-BASELINE`、`WF-DOCS-REPORT`、`WF-SNAPSHOT-COVERAGE`。以下只是该阶段独立复验要点，原始完整断言仍以阶段计划、A2任务、r2补正复验及安全模型为准。已有正式测试若等价覆盖历史探针，必须明确比较断言与触发条件；旧探针不可用时不能默默跳过。后续阶段按第1节建立新的完整矩阵，不套用本节作为全部需求。

| 专项 | 本阶段必须检查／观察 |
| --- | --- |
| C1 资源隔离 | A1/A2/reviewer Compose 所有权与命名空间独立；清理只作用自有资源；无关资源前后不变 |
| C2 成本候选流程 | 候选前仅 schema/静态验权与可信权限集合检查；命中用原快照/持久化事实，仍走 A1 动态验权、proof 登记与完整意图比较；miss 后任意资源/报价解析失败都安全重查候选 |
| C3 旧行保全 | 使用补正的隔离 sidecar；001/003→最新迁移后旧七表原列/行及非零预留、撤销、证据保持，非法升级旧数据和完整迁移记录不变 |
| C4 事件/候选保全 | RESERVE 对应 seq=0，SETTLE/RELEASE 对应 seq=1；唯一预留与互斥终局；事件/节点不能 UPDATE/DELETE；合法已接受操作永久保全 |
| C5 租约 | claim/终局条件同时绑定 owner、fencing version、合法状态和锁后 DB 当前时刻下的有效 expiry；即使无新 owner，过期旧 worker 也不能写终局；UNKNOWN claim 保持 UNKNOWN，EXECUTING 接管先对账 |

| P15-CORE 分层与独立 A1 回归 | 四工具严格参数/资源、空/缺失权限集、跨租户、错快照等负例为零效果/零预留；不声称真实密码验证，不免除后段完整P15真实验权。`WF-A1-REGRESSION` 独立列出 A1 全套与根同 ID 重建拒绝，非零迁移同时映射P19，不能用P15替代它们 |
| P20 数据库防绕过 | 直接 SQL 改意图/成本/首次证据、改删事件/节点、直接删操作或先改删事件再删操作、删除/重建已接受路径、非法迁移/双终局被拒绝；原账本/证据不变，合法计数/撤销/状态 UPDATE 仍有效 |

## 7. 结论、问题闭环与阶段停止

- `ACCEPTED`：仅对明确当前阶段与冻结版本作出建议；所有当前阶段必需项已有足够独立证据，阻断缺陷全部由本轮 reviewer 证据关闭，必跑验证未缺失。无发现不等于完整安全证明。
- `NOT_ACCEPTED`：发现当前阶段违反需求/不变量、回归、证据造假/遗漏或必需覆盖不足。列出稳定 issue ID、严重度、阻断理由、触发条件、范围、证据、补正要求和复验方法，交主控在当前阶段自动委派补正。
- `BLOCKED`：版本漂移、资源不安全、工具/额度/环境阻碍、需求矛盾或阶段必需外部依赖未就绪，无法完成有效审查。明确最小复现、已有阶段成果与解除条件；不能伪 PASS，也不能无进展无限重试。
- Fresh reviewer 承接问题台账，不承接“前轮应该已经通过”的结论。已关闭项可被新回归重新打开；实现者只能标 `FIXED_PENDING_REVIEW`，不能自行关闭。问题降级/移出阶段须有原始需求与真实证据，主控或实施者不能为放行改测试预期、移除断言、skip或缩减矩阵。
- 主控必须读回完整报告、抽查实际证据、核对候选指纹与问题关闭依据，然后记录当前阶段 ACCEPTED 或继续补正。重大意见分歧交用户，不由主控无证据压过 reviewer。
- 当前阶段通过后留下完整审查、问题台账、证据入口、已验证范围、未完成/B依赖及下一阶段审批事项，进入等待用户批准状态。A2.1 ACCEPTED ≠完整 A2 ACCEPTED ≠项目完成；不自动开下一阶段、不提交或发布。
